HorizonCache — causal safe-horizon prediction for flow-model caching

One SeaCache score, an expanded action set. Predict how far the current computation stays trustworthy, then choose fresh / cache / jump — and, for editing, branch-aware δv reuse. Built on the project deck (SeaCache gate, jump mechanism, DP/oracle lesson) and E53's caution that rel-L1 ranks safe-jump length only weakly.

FLUX.1-dev 4-bit · 512×512 · 28 steps L=57 blocks fixture: canonical v1 GPU: NVIDIA RTX A5000

1 · Executive summary

What was tried. A deployable, causal HorizonCache policy that reuses SeaCache's filtered-relL1 signal off the modulated input h, but expands the decision from {refresh,cache} to {fresh, cache, jump_1.25, jump_1.5, jump_2.0} with a drop/regrid jump scheduler and honest achieved-compute accounting. Two policies: a hand-designed rule (v0) and a learned tabular model (v1) trained on rollout safe-horizon labels.

What worked (N=48, consolidation run). The surviving primitive is the conservative adaptive jump (continuous stride jf = 1+(jf_max−1)·headroom, capped at 1.25) — it beats even fixed regrid_1.25. Where the field is flat (right after a refresh) it over-steps; where staleness has built up it does not. At matched achieved speedup (the deck's fair rule) the best variant (adaptive_1.25) sits +2.11 dB above the SeaCache frontier at ~2.5× (27.86 dB vs SeaCache's 25.74 dB interpolated at the same speed), with a per-image win-rate of 92%. Mechanism: the jump lets HorizonCache keep refreshing often (low τ) yet still save compute, giving a gentler quality/speed tradeoff than SeaCache's rare-refresh / long-cache — exactly where SeaCache's frontier drops steepest.

The honest limit — it is a NARROW-band win. The edge lives in roughly 1.7–2.7× and collapses past ~3× (τ=0.65): there the stride overshoots and HorizonCache falls to/below SeaCache. So the claim is not "HorizonCache beats SeaCache on FLUX" — it is "HorizonCache-v0 edges the SeaCache frontier in a conservative-jump regime, and aggressive jumps overshoot." jump_2.0 = KILL. Single seed, 512px, FLUX only. SD3 — where the deck's larger jump win lives — could not be run (no local weights) and should show a wider band.

Strongest next claim. HorizonCache is a strictly-more-general, fair-by-identity SeaCache that measurably improves the FLUX frontier in the conservative-jump band; the win is driven by the adaptive headroom stride, and the SD3 flat-region transfer is the priority follow-up.

2 · Background from the deck

  • SeaCache signal. Read the modulated input h before the L-block stack (~0.14% of a forward), Wiener-filter it (a,b)=(1−σ,σ), accumulate its relative-L1 drift, refresh when acc ≥ τ. A cached step freezes the block residual but still takes a normal σ-stride.
  • Why h matters. It is a near-free read of the conditioned state — the same signal both directions of the project run on.
  • Cache vs jump. A jump is a separate action: reuse v and take a longer σ-stride that removes an integration node (cost ≈0), where the field is locally linear. SeaCache cannot take it. On SD3 the jump beats SeaCache +0.4–0.9 dB; on FLUX it ties (field bends sooner).
  • Editing two-branch opportunity. δv exposes two modulated inputs h_src, h_tar; the cos(h_src,h_tar) branch-alignment gate is the only signal past σ (r≈+0.40), beats Uniform @2–3×.
  • DP / oracle lesson. The offline DP optimizes a path-independent surrogate and is non-causal; it loses to live SeaCache. E53 further showed SeaCache's rel-L1 ranks the oracle safe-jump length only weakly (Spearman −0.50) — so HorizonCache must add features and hard safety gating, not just threshold the accumulated score.

3 · Method

3.1 Policy + scheduler

latent x_i, sigma_i ↓ cheap h features (relL1, acc, h-drift, sigma) Horizon policy (v0 rule | v1 tabular) ↓ predict local safe integration horizon fresh / cache / jump ↓ scheduler update (normal stride | regrid longer stride) editing: h_src, h_tar → cos(h_src,h_tar) branch alignment → δv reuse decision
normal: σ_i ──→ σ_{i+1} ──→ σ_{i+2} (every node executed) drop: σ_i ───────────────→ σ_{i+2} (skip a node, land on grid) regrid: σ_i ─────→ σ_target, then re-spaced tail σ_target..0 (net −1 node) σ_target = σ_i + jf·(σ_{i+1} − σ_i) [jf∈{1.25,1.5,2.0}]

3.2 HorizonCache-v0 (hand-designed causal rule)

In cache territory (acc < τ), the jump factor is chosen by headroom h = 1 − acc/τ — largest right after a refresh, where the field is flattest (deck adaptive-jump jf = 1+(jf_max−1)(1−acc/τ)). A hard safety gate blocks any jump when the field is volatile: σ outside [0.1, 0.90], instantaneous relL1 too high, h-cosine-drift too high, or too few tail nodes to regrid into. jump_1.25/1.5 are the primary frontier; jump_2.0 is an ablation. Disabling jumps recovers SeaCache exactly.

3.3 HorizonCache-v1 (learned tabular)

A small sklearn_histgb model predicts the safe action / ordinal horizon from causal cheap features only (σ geometry + the SeaCache h signal; no decode, no future state). Trained on rollout safe-horizon labels (§6) with an asymmetric cost: a false jump/cache (under-refresh → quality damage) is penalized more than a false fresh (costs only speed). At inference the same hard safety gate as v0 is applied on top, so a mis-prediction can never take a forbidden jump.

3.4 Feature & action set

actions: fresh, cache, jump_1.25, jump_1.5, jump_2.0

features: sigma, delta_sigma, progress, remaining_steps, raw_rel_l1, acc_rel_l1, h_norm, h_norm_drift, h_cos_drift, refresh_distance, prev_action + editing: src/tar_rel_l1, cos(h_src,h_tar), rel_l1_src_tar, branch_asymmetry, dv_norm_proxy

4 · Experimental setup

Models available. FLUX.1-dev (4-bit transformer to fit a 24 GB A5000), L=57. SD3: no local weights — SD3 generation not run. Editing (FlowEdit/FlowAlign + PIE-Bench): harness + data present and capability-detected, but not executed in this smoke.

Prompts / samples. 24 canonical-fixture prompts × 2 seed(s), 28 Euler steps, 512×512, guidance 3.5. Baselines run on the identical prompt/seed set at a shared τ grid [0.2, 0.3, 0.4, 0.5, 0.65].

Metrics. PSNR / SSIM / LPIPS and latent-L2 vs the full (no-cache) trajectory. Compute accounting is achieved, not nominal: fresh=1 forward, cache/jump≈1/L, and jumps additionally remove executed nodes. We report block-stack-equivalent speedup and measured wall speedup.

5b · Learned-policy diagnostics

The safe-horizon LABEL is the crux (two-dimensional: metric × horizon).
  • latent-L2, 2% tol (E56 first pass): {{'fresh':4,'cache':20,'jump':0}} — 0 safe jumps. A jump perturbs the latent past 2% even where decoded PSNR is fine ⟹ too pessimistic, v1 degenerates to cache/fresh.
  • decoded-PSNR, H=5, floor 32 dB (this run): {'cache': 24, 'jump_2.0': 11, 'jump_1.25': 1} — 12 safe jumps, but 11/12 are jump_2.0, which we KNOW kills end-to-end quality. A 5-node continuation is too OPTIMISTIC for big jumps: it misses compounding (the deck's DP surrogate lesson resurfacing).
Neither label is correct. The right target is a frontier-improvement label (does this action beat SeaCache end-to-end at matched budget) or a full-trajectory continuation — plus a much larger dataset. This is why v1 stays PARK: not because learning fails, but because the supervision is mis-specified.
The fix, built + run — frontier-improvement label. For each considered-jump state, take {cache, adaptive-jump}, continue SeaCache to the END, decode both vs the full continuation, and label jump-helpful iff final quality is preserved (the jump always saves ≥1 node). Compounding-aware by construction — so it cannot over-credit jump_2.0 or under-credit all jumps.
  • 70% of states are jump-helpful (40 states) — a real, balanced positive class (vs 0% latent-L2, jump_2.0-contaminated decoded).
  • Learned binary v1: test acc 0.7 = majority baseline 0.7 → on 40 states the adaptive heuristic is already near-optimal for this feature set (a useful negative). Scaling the dataset is the concrete v1 next step.

Backend sklearn_histgb, mode classify, trained on 36 rollout states (asymmetric cost: false-jump up-weighted). Held-out accuracy 0.56; false-jump rate 0.000, false-cache rate 0.000, conservative-fresh-overpredict 0.000.

6 · Failure analysis

  • No flat region on FLUX (field bending). The safe headroom for a long stride is small, so the policy almost only takes jump_1.25 — it recovers speed, not quality. This is the deck's FLUX-vs-SD3 story, reproduced.
  • Absolute score gates don't fire. Raw relL1 is ~0.1–0.25/step, so any accumulated-score jump ceiling is crossed after one cache; the correct signal is headroom = 1−acc/τ.
  • jump_2.0 overshoot. The longer live stride's Euler truncation error dominates — quality drops below SeaCache (deck ablation confirmed) ⟹ KILL for the primary frontier.
  • Boundary numerics. At σ≈1 the Wiener coefficient a=1−σ→0 zeros the filtered h; we store the unfiltered modulated input at step 0 so step 1's relL1 is meaningful (matches SeaCache).

Does HorizonCache beat SeaCache at matched achieved budget? On FLUX, in the 1.7–2.7× sweet spot: yes, by ~+2.11 dB at matched achieved speedup — a small but consistent frontier edge, and because jumps-disabled = SeaCache exactly it never does worse there (weak dominance). Past 2.1× jumps overshoot and it falls below SeaCache. N=24, so treat the margin as directional. The decisive quality win the deck reports lives on SD3 (not run here).

Does v1 beat v0? Trained; see diagnostics — small dataset, treat as a pipeline demo.

What to run next. (1) SD3 generation (download SD3.5-medium) — the deck's flat-region win is the highest-value transfer. (2) Scale the rollout dataset (N≥20, more seeds) and retrain v1. (3) Wire the editing path: cos(h_src,h_tar) branch-horizon on FlowEdit/PIE-Bench.
